# Phase 9.5 dogfooding and reliability record

## Scope and method

Interactive checks used Koren Code Editor on Linux x86_64 with WebKitGTK under Xvfb/Openbox. Debugging and language-server workflows used disposable programs and an isolated home directory. No demonstration edits were made in the Koren repository. Interactive acceptance is reported separately from automated checks.

Earlier Phase 9.5 checks remain recorded below: project search, Unicode editing and saving, rename with an open tab, root-level Git selection, extension commands, graphical shell approval, and approved Cargo execution were exercised in the desktop window. The root repository selector fix and its frontend regression test are in the earlier Phase 9.5 commit history.

## Real GDB DAP

GDB 17.2 was verified locally with `gdb --interpreter=dap`; its DAP initialize request succeeded and the build reported Python support. A temporary Rust program was compiled with debug symbols. Koren was configured to start `/usr/bin/gdb --interpreter=dap` with the fixture executable and working directory. The desktop displayed the exact adapter and target details and required explicit approval before launch.

The real session initialized, accepted a source breakpoint, launched, stopped at that breakpoint, displayed the source execution line, returned `main::main` in the stack, and showed the local `answer = 40`. Step Over advanced execution; Continue completed the fixture and showed `dap fixture: 80`; a separate Stop ended a session in the `terminated` state. The installed GDB emitted `No source file named ...` and reported a pending breakpoint before the executable was loaded, then resolved and hit it after launch. This is a pre-load diagnostic from GDB, not evidence of a failed breakpoint.

The real window exposed a Koren defect before the successful run: editor tabs carry workspace-relative paths, while the DAP breakpoint API requires an absolute source path. Koren rejected the click with `debug breakpoint source must be absolute`. The frontend now resolves workspace-relative source paths before requesting breakpoints; focused tests cover Unix paths, Windows paths, and rejection of a relative workspace root. Fix committed as `82f935b` (`fix(debug): resolve workspace paths for breakpoints`).

This verifies GDB 17.2's native DAP launch path on this Linux host. Other DAP adapters and Windows/macOS desktop behavior were not tested.

## Real rust-analyzer

The installed `rust-analyzer` was the rustup shim and initially had no component installed for the active stable toolchain. The official stable component was installed locally and reported `rust-analyzer 1.99.1 (58cf8f9 2026-10-13)`. A disposable Cargo project and a temporary Rust extension configuration pointed Koren at the direct analyzer executable, with explicit `HOME`, `CARGO_HOME`, `RUSTUP_HOME`, and `PATH` values because the language-server manager starts processes with a cleared environment. Koren displayed a graphical authorization request before starting it. The running analyzer and its proc-macro helper processes were observed; they exited when Koren was closed.

The session produced a real unresolved-name diagnostic in Problems. After editing the source to remove the error, the old diagnostic disappeared. Hover showed rust-analyzer's inferred `i32` type information, and completion offered the local `answer` value. The source was edited rapidly and the editor remained responsive; a second open document was used during the same session. These checks confirm basic initialization, workspace loading, synchronization, diagnostics, hover, completion, and shutdown.

The final interactive run used a disposable Cargo workspace and the real rustup `rust-analyzer 1.99.1`. The Problems panel showed its syntax diagnostics and unused-variable warning. Ctrl+. on the unused variable returned rust-analyzer's `_value` quick fix. Koren displayed the Before/After edit preview, the user-confirmation step was accepted, and the editor changed `let value = 1` to `let _value = 1` at a newer document revision. The action was verified in the editor; an independent on-disk save verification after that exact action was not completed. Real Go to Definition remains inconclusive: the analyzer returned real hover data for `helper::answer`, but the final F12 attempt did not visibly open `src/helper.rs` or establish the destination line and column. Same-file navigation, multiple-result selection, empty/unsupported/stale responses, and missing-target behavior therefore remain unverified interactively. The selection and stale-result helpers retain automated coverage.

The restart exercise also reproduced old syntax diagnostics after closing and reopening the same source while the language server remained active. LSP versions had restarted at `1` on each open, allowing a delayed publication from the old open to match the new one. `LspDocumentSync` now uses a monotonically increasing per-server version across opens, edits, and closes; a regression test verifies that an old version cannot match after reopen. The live GUI run on the repaired build showed the unresolved-name diagnostic but did not deterministically reproduce the delayed-publication race again.

The analyzer configuration was specific to the disposable fixture and did not modify the repository's extension catalog or weaken execution approvals. Analyzer-triggered Cargo/build-script behavior was not separately measured.

## External save conflicts

The editor opened a disposable `conflict.txt`; an external process independently replaced it with Unicode text (`external version – 雪`). Koren's save opened the “File changed outside Koren” dialog. Expanding the preview showed the external text. Choosing Reload put that exact text in the editor and left the document clean at a newer revision.

A second external revision was then written while Koren held a different unsaved buffer. The dialog preview showed `new external revision`. Choosing the explicit Overwrite action wrote `overwrite from Koren` to disk and returned the document to a clean state. The document service's tests additionally cover external deletion, changed-again detection, reload revision increments, and refusal to silently save over newer contents. Rapid changes during a conflict and conflict while inspections run were not separately exercised in the GUI.

## Restart, session restoration, and unsaved-document recovery

With an isolated `HOME`, the desktop app was closed and relaunched without a command-line workspace argument. It restored the last workspace and `src/main.rs` tab from WebKit local storage. The persisted session record also includes tab order, active tab, and active standard panel; layout dimensions are viewport-bounded on restore, and theme remains an independent preference. The earlier extension settings and inspection profile round-trip tests remain in place. In the observed restart the Light theme remained selected. Extension enablement and activation are intentionally not restored; the user explicitly enabled, activated, and approved the real rust-analyzer again. Running tasks, terminals, language servers, debuggers, and other child processes are not restarted by session restore.

The first folder-picker failure was an Xvfb interaction mistake: Openbox/GTK displayed the native chooser, but the automation clicks landed in its location/search controls rather than selecting the folder. The interaction did not demonstrate a WebView ownership failure. Portal involvement on the normal Wayland desktop was not isolated, so no portal-wide conclusion is claimed. To make startup deterministic for users and desktop automation, `koren-code --workspace PATH` now validates that the supplied path is an existing, non-symlink directory, canonicalizes it, and opens it through the normal workspace API; it does not grant extra filesystem or process permissions. A real user-folder selection was not separately repeated after adding the CLI option.

Abrupt-exit recovery is implemented in the per-user `koren-code/recovery` data directory. Dirty documents are snapshotted asynchronously after a short idle delay and after the revision pipeline flushes. The store is bounded to 1 MiB per document, 20 documents, and 8 MiB total, expires entries after 30 days, writes atomically, and uses mode `0700` for its directory and `0600` for snapshot files on Unix. It records workspace, relative path, base-file SHA-256, document revision, and text without logging source contents. Startup presents explicit Restore and Discard actions. When the backing file still matches, restore reopens that document; when it changed or disappeared, restore creates a new workspace file so it cannot overwrite the current file. A real desktop test edited a disposable Rust buffer, observed a private snapshot file, killed the app, relaunched, saw the recovery prompt, and restored the text. A second test changed the backing file while the app was closed; restore created a new `recovered-main-…rs` file and the external replacement remained intact. A post-restore save removed its snapshot. Explicit Discard, multi-document storage, and expiry cleanup are also covered by store tests.

The old per-user test home was kept separate from real user settings and project files. Corrupt or unsupported session records fall back to a clean session; invalid recovery records are ignored. A missing workspace does not prevent startup, and the recovery record remains available for explicit recovery or expiry cleanup. Extension activation state is not persisted, and extension settings/profile persistence is separate from workspace session recovery.

## Final stabilization changes

The frontend now stores a versioned session record in WebKit local storage containing the workspace path, open workspace-relative tabs, active tab, and active standard panel. On startup it reopens the workspace and files in order, selects the prior active tab and panel, and reports files that no longer exist. It does not auto-start a terminal, debugger, language server, or extension. A missing workspace leaves the editor available and reports that the user must choose another. Unsupported or corrupt session records are ignored. Saved explorer and bottom-panel sizes are bounded to the current window at startup and resize; theme selection continues to use its existing independent preference. Corrupt, outdated-schema, unsafe-path, viewport-clamp, and multiple-definition-selection cases have frontend regression tests.

The CLI startup path bypasses the chooser for a named workspace; normal picker behavior remains in place. Same-file/cross-file Go to Definition is still not acceptance-tested in the actual app. Session restoration and abrupt process recovery were observed on Linux/WebKitGTK with the isolated test home; different desktop backends and power-loss durability were not tested.

Go to Definition now prompts when the language service returns multiple locations, ignores invalid selections, and reports an empty or unsupported result. Navigation retains the existing workspace boundary and opens the selected target through the document service, preserving an already-open target buffer. The multi-location selection helper is covered by frontend tests. Real same-file/cross-file rust-analyzer navigation, UTF-16 positioning, stale-result timing, and dirty-target behavior have not yet been completed in the desktop UI.

Real rust-analyzer quick-fix preview and confirmation are now accepted interactively. Go to Definition remains unverified end to end, so Phase 9.5 is still partial.

## Definition navigation and final interactive acceptance

The original F12 route was registered only as a CodeMirror editor key binding. In the WebKitGTK desktop window, invoking F12 did not reach the navigation workflow. The same definition request, destination handling, and active document service worked when called through the UI command route. F12 is now handled in a document-level capture listener and dispatches to that shared workflow; this avoids depending on the editor keymap receiving the key. The root cause is localized to keyboard-event dispatch at the editor-keymap boundary in the tested WebKitGTK build; no claim is made that WebKitGTK globally consumes F12. The Navigate menu and command palette use the same command.

The LSP client advertises definition-link support and accepts `Location`, arrays of `Location`, `LocationLink`, arrays of `LocationLink`, and `null`. For links, `targetSelectionRange` takes precedence over `targetRange`. URI conversion decodes escaped spaces and Unicode, rejects malformed, remote, and out-of-workspace paths, and navigation clamps UTF-16 positions to the destination document. A destination opens or reuses its tab, becomes active, scrolls to the selected range, and receives focus; an existing dirty buffer remains in memory. Empty results and missing server/capability cases produce an informational message. Frontend and bridge/LSP tests cover the response shapes, path checks, UTF-16 positions, stale revisions, command routing, multiple results, empty results, and unsupported service feedback.

On Linux/WebKitGTK with the real `rust-analyzer 1.99.1` against the disposable Cargo workspace, F12 navigated from `helper::answer()` in `src/main.rs` to `src/helper.rs`, with the destination selected at line 1, column 8. A same-file call selected its declaration. A `#[path = "naïve.rs"]` module verified a Unicode filename and `café` declaration; after link support was enabled, the real analyzer returned a definition link and navigation selected the declaration at line 4, column 8. The Navigate menu produced the empty-result message when invoked at a location without a definition; the command palette opened the same destination from a valid call. This confirms the F12, menu, and palette paths. Multiple real analyzer destinations were not available in this fixture, so the selection prompt is covered by automated tests instead.

The real rust-analyzer quick fix was repeated on an unused local in `src/naïve.rs`: the diagnostic offered `_value`, Koren displayed the Before/After preview, the change was accepted and saved, and an independent disk read confirmed `let _value = 1;`.

Layout persistence was exercised by widening the explorer and resizing the bottom panel, selecting Problems, closing the app, and relaunching it without a workspace argument under the same isolated home. The wider explorer, shortened panel, active panel, workspace, and open file were restored. Recovery was tested with a deleted backing file: after an abrupt app exit, Restore opened a new `recovered-main-…rs` file with the complete unsaved buffer and left the original path absent; saving the recovered file preserved the content. A second snapshot was explicitly discarded, and the discarded draft was absent from the recovery store and was not written into the backing file. These were Linux/WebKitGTK tests using disposable files only.

The live checks establish Linux/WebKitGTK behavior. Windows/macOS, multiple real definition targets, and power-loss durability remain untested. Dirty-target preservation follows the existing document-service reuse path and is covered at the service layer; it was not separately driven with an already-dirty definition target in this final UI pass.

The repository has document-service tests for conflict preview/reload/overwrite, external changes, deleted files, and dirty close; settings tests cover legacy migration and profile round trips; frontend tests cover bounded theme/layout state helpers and definition result selection. LSP synchronization tests cover monotonically increasing document versions after close and reopen. Final verification passed `python3 scripts/check.py`, `python3 scripts/pr_check.py`, and `cargo +1.85.0 check --workspace --locked`. The PR check included strict Clippy, all Rust unit and doc tests (including 28 Koren Code Editor binary tests), 21 Python tests, 67 frontend tests, typecheck, lint, production bundle, architecture checks, clean workspace build, optimized editor build, and Linux desktop launch smoke. The final WebKitGTK/Xvfb smoke reported 170.6 ms startup and 414,820 KiB process-tree RSS. This is a launch measurement, not a substitute for the separately reported interactive checks.

## Performance boundaries

The three earlier no-tool desktop smoke samples remain the baseline: median visible window 174.2 ms and process-tree RSS 395,056 KiB at one second. The final PR smoke during this completion run reported 227.1 ms and 405,200 KiB. These are Linux/Xvfb smoke measurements, not interactive latency targets. A real rust-analyzer process was sampled at about 646 MiB RSS while indexing the small fixture, with two proc-macro helpers around 27 MiB each; Koren's process was about 204 MiB at that moment. These are single `ps` samples, not peak or steady-state measurements, and shared memory is not separated.

LSP initialization-to-ready time, edit-to-diagnostic latency, real debugger startup-to-first-stop, conflict-preview latency, restored-session latency, idle CPU with real services, and per-process WebKit memory were not instrumented. They remain unmeasured rather than inferred from the fake-server or launch-smoke benchmarks. See [BENCHMARKS.md](../BENCHMARKS.md) for the prior workload boundaries.
